> Semantica 由 Semantica 团队在开放治理模式下维护，并接受社区贡献。


## 角色

- **维护者** —— Semantica 团队：评审并合并 PR、管理发布与代码质量、确定项目方向与社区标准。
- **贡献者** —— 提交代码、文档与 bug 报告，协助处理 issue 和评审。在 [CONTRIBUTORS.md](https://github.com/semantica-agi/semantica/blob/main/CONTRIBUTORS.md) 中获得致谢。
- **社区成员** —— 使用 Semantica、提供反馈、分享使用场景，并参与 GitHub Discussions 与 Discord。


## 决策流程

### 代码变更

<Steps>
  <Step title="提案">开一个 GitHub Issue 描述该变更。</Step>
  <Step title="讨论">就方法与范围进行社区讨论。</Step>
  <Step title="实现">提交包含该变更的 pull request。</Step>
  <Step title="评审">至少一名维护者评审该 PR。</Step>
  <Step title="合并">CI 通过且维护者批准后合并。</Step>
</Steps>

### 重大决策

- 在 GitHub Issues 中发布 RFC
- 至少 1 周的社区讨论期
- 维护者根据社区反馈与技术可行性做出决定


## 发布

Semantica 遵循**语义化版本（Semantic Versioning）**（`MAJOR.MINOR.PATCH`）：

| 级别 | 触发条件 | 节奏 |
| :------- | :--------- | :--------- |
| MAJOR | 破坏性变更 | 每季度或按需 |
| MINOR | 新功能（向后兼容） | 每月或就绪时 |
| PATCH | Bug 修复（向后兼容） | 随修复发布 |


## 代码评审

**评审标准：**功能性、代码质量、测试、文档、性能、安全性。

**时间线：**48 小时内完成初次评审；7 天内完成跟进。

**评审者指南：**保持建设性、说明理由、提出替代方案。

**贡献者指南：**及时回应评论、不清楚时提问、乐于接受反馈。


## 沟通

- **GitHub Issues**：bug 报告、功能请求与问题
- **GitHub PR**：代码贡献
- **GitHub Discussions**：社区交流
- **安全公告**：[私下报告安全问题](https://github.com/semantica-agi/semantica/security/advisories/new)


## 项目目标

- **易用性** —— 易于使用和理解：合理的默认值、清晰的文档、最少的繁文缛节。
- **可靠性** —— 生产级质量：在各种 Python 版本、平台与真实工作负载下经过测试。
- **性能** —— 高效且可扩展：从单机 notebook 到企业级图数据库。
- **可扩展性** —— 通过 `PluginRegistry` 模式，轻松用插件与自定义模块进行扩展。
- **社区** —— 友好且包容：各种背景与经验水平的人都能做出贡献并获得致谢。
